### 前言

业务建模平时最大的问题，不是没思路，而是没标准。拆表还是合表，状态怎么定，全靠主观判断，最后变成争吵。加上现在 AI 写代码，没有约束，生成的模型更是经不起推敲。
我们需要一套客观的工程规则，把建模从“凭感觉”变成“能算账”。
这套规则解决两个层面的问题：
**6个领域**，解决逻辑关注点，防止属性纠缠；
**10条铁律**，解决落地关注点，守住架构底线。

---
### 一、 6个领域：按性质分家
传统的建模习惯，是把一个业务对象的属性全塞进一张表。这会导致严重的逻辑纠缠。我们的做法是，先按性质把属性强行切分到 6个领域：
1. **身份**：是什么、属于谁、作用于谁。这是地基，一旦创建绝对不可变。
2. **需求**：要什么。
3. **计划**：打算怎么做。
4. **执行**：实际怎么做。
5. **结果**：状态怎样。
6. **约束**：什么条件限制。
这 6 个领域的核心是正交，互不污染。比如，计划是意图，执行是事实。事实发生了，不能去篡改原来的意图；身份是地基，状态是楼上，业务流转绝不能动摇身份。
### 二、 10条铁律与真实案例
规则不落地，就是空谈。看看常见的反面案例：
```java
class Order {
    String status; // DRAFT, APPROVED, SHIPPED, CANCELLED, SHIPPED_AND_CANCELLED...
    int qty;       // 有时是计划量，有时是实际量
}
```
这种设计，业务一变就会死：
第一，状态组合爆炸。审核和发货是两个生命周期，揉在一个字段里，必然出现 `SHIPPED_AND_CANCELLED` 这种缝合怪，最后 if-else 写到手软。违反了**“异空必拆维”**铁律。
第二，意图和事实混淆。`qty` 到底存的是客户要的量，还是仓库实际出的量？一旦混用，后续查偏差、做报表全成了一笔糊涂账。违反了**“意图实现解耦”**铁律。
第三，规则藏在代码里。限额 10000 写在 `validate()` 方法里，前端想做个输入校验都没法获取，改个限额还要改代码发版。违反了**“约束显式化”**铁律。
按铁律来改，就是强行拆维：
*   **身份域**：确定单据类型和归属客户（不可变锚点）。
*   **计划域**：plannedQty（意图，留存历史）。
*   **执行域**：actualQty（事实，实时更新）。
*   **结果域**：auditStatus（审核状态）与 shipStatus（发货状态）独立流转。
*   **约束域**：maxAmount（限额规则显式记录为字段）。
拆完之后，改发货状态不会影响审核状态，查偏差直接相减。逻辑清晰，牵一发不动全身。
### 三、 底线与变通：工程不是教条
规则看起来很严，但工程不是教条。这 10 条铁律有明确的适用边界。
比如，计划和执行必须分开？如果只是一个内部简单领用单，不需要追踪偏差，一个 `qty` 足矣，硬拆反而增加复杂度。
那拆不拆到底谁说了算？算账说了算。我们有一个复杂度测算公式：如果状态 A 有 3 个值，状态 B 有 4 个值，合在一起是 12 种组合，拆开只需处理 7 种逻辑。组合数超过 10，必须拆；没超过，看独立触达率。用数据代替争吵。
另外，工程总有妥协。为了查询快加冗余字段，可以。但必须在注释中标记 `[REDUNDANCY]`。允许妥协，但不能隐式妥协，让后人踩坑。
### 四、 约束 AI 的硬框架
这套规则当前最大的附加价值，是能约束 AI。
你给 AI 一套业务描述，它经常给你生成大杂烩。现在，你把 10 条铁律喂给它，强迫它先填“6个领域归属表”，算完账，再写代码。AI 的输出立刻变得规整且可控。
### 结语
建模不该是玄学。6个领域保证逻辑不乱，10条铁律保证底线不破，一个算账公式解决架构争议。
