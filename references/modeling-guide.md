# 业务建模指导手册

> **目标**：属性拆分标准化判定，人可评审，AI可执行。

---

## 一、核心准则（十条铁律）

> **重要**：以下准则为硬性约束，设计与评审时必须逐条核对。

| 序号 | 准则 | 明确定义 | 验收标准 | 示例 |
|------|------|---------|---------|------|
| 1 | **六域正交** | 属性归属严格限定于身份上下文、需求、计划、执行、结果、约束六个域 | 跨域属性必须重构拆分 | ✅ 报价单的计划域有`targetQty`，执行域有`actualQty` ❌ 混合为`qty` |
| 2 | **异空必拆维** | 不同业务子空间（如报价态、合同态）的生命周期正交 | 按空间拆分独立枚举；禁止数据库存综合状态，前端拼接 | ✅ 报价态、合同态各独立枚举 ❌ `待发货=已付+未发`存数据库 |
| 3 | **并发取积** | 同空间内状态并发时，拆为多维独立枚举取笛卡尔积 | 禁止单枚举堆砌并发状态 | ✅ `auditStatus` × `refundStatus` ❌ `AUDITING_REFUNDING`混合态 |
| 4 | **状态互斥穷尽** | 同空间单维枚举取值绝对互斥且完全穷尽 | 根除非穷举盲区 | ✅ `DRAFT/SUBMITTED/APPROVED/REJECTED` ❌ 缺少`REVOKED`导致盲区 |
| 5 | **时序事实追加** | 结果域数据强绑定时间戳绝对不可变 | 状态推进靠按时序追加新事实；插流水表而非覆盖 | ✅ `List<PaymentRecord>`追加 ❌ 覆盖`paymentStatus` |
| 6 | **意图实现解耦** | 计划域锁定目标契约，执行域承载易变细节 | 二者零耦合 | ✅ `plannedQty`与`executedQty`分离 ❌ 单一`qty`混用 |
| 7 | **约束显式化** | 业务规则脱离代码控制流 | 沉淀为模型维度的独立规约或属性 | ✅ `maxAmount`字段 ❌ 隐含在`validate()`方法中 |
| 8 | **类型极简降级** | 属性类型穷尽至基础数据类型或值对象 | 拒绝结构体黑盒；扩展字段走KV表而非主表 | ✅ `BigDecimal amount` ❌ 主表加`extra_data` JSON |
| 9 | **流转闭环兜底** | 状态机必含单一起始态与可达终态 | 根除悬停僵尸态 | ✅ `DRAFT`起始、`COMPLETED`终态 ❌ 无终态导致僵尸 |
| 10 | **上下文绝缘** | 同名词不同业务域必须物理或逻辑隔离 | 扼杀上帝模型 | ✅ `OrderCustomer`/`ContractCustomer` ❌ 全局`Customer`混杂多职责 |

## 二、排除特例

> **说明**：以下工程实践虽违背教科书范式，但属于合理设计，评审时不计入问题。

| 类别 | 特例场景 | 方向性描述 |
|------|----------|------------|
| **性能优化** | 冗余存储 | 为减少关联查询，将关联数据冗余存储于当前实体 |
| **性能优化** | 预计算结果 | 提前计算并存储结果，避免实时计算开销 |
| **性能优化** | 查询缓存 | 高频查询数据的缓存副本 |
| **历史快照** | 时间点数据 | 保存业务发生时的状态，而非当前最新值 |
| **并发控制** | 乐观锁机制 | 用于防止并发更新冲突的技术标记 |
| **数据管理** | 软删除机制 | 逻辑删除而非物理删除的实现方式 |
| **数据隔离** | 多租户机制 | 数据隔离的技术实现 |
| **数据追踪** | 审计追踪机制 | 记录数据变更的来源和时间 |
| **扩展性** | 动态属性存储 | 不确定扩展属性的存储方案 |
| **数据迁移** | 临时迁移标记 | 批量导入、迁移过程的临时辅助 |

## 三、建模步骤

| 步骤 | 动作 | 判定点 |
|------|------|--------|
| 1 | 列出所有状态值 | — |
| 2 | 按六域分组 | 身份上下文/需求/计划/执行/结果/约束 |
| 3 | 每组内部过十条铁律 | 命中任意→继续拆 |
| 4 | 命名维度 | 状态用`_status`，标记用`is_` |
| 5 | 定义流转 | 枚举值、流转路径、前置条件 |
| 6 | 组合检查 | 组合行为=各自规则加起来 |
| 7 | 物理落地权衡 | 有独立查询/权限需求→拆；无→可合 |
| 8 | **复杂度测算** | 算组合乘数、嵌套深度、独立触达率，防止过度设计 |

## 四、复杂度分析与过度设计防护

> **核心思想**：建模追求科学正确，但要防止过度工程。通过复杂度推演，在"绝对纯洁"和"刚刚好的妥协"之间找平衡。

### 四步推演法

| 步骤 | 动作 | 目的 |
|------|------|------|
| 1 | 粗建模（快） | 凭经验先把字段定下来 |
| 2 | 过手册（准） | 用十条铁律扫一遍，砍掉明显违背常识的 |
| 3 | 穷举 Case（全） | 结合上下游，枚举所有业务走向 |
| 4 | 算复杂度账（决） | 算账决定是否真正落地拆分 |

### 复杂度测算维度

完成正交拆分建议后，执行以下"算账"动作，决定是否真正落地拆分：

#### 1. 组合乘数

候选维度 A 有 N 个枚举值，候选维度 B 有 M 个枚举值。

| 情况 | 判定 | 说明 |
|------|------|------|
| 组合复杂度高 | 考虑拆分 | 代码维护成本指数上升 |
| 组合复杂度低 | 倾向合并 | 写几个分支就完事，拆了反而增加表关联成本 |

**思路**：不拆时要处理 N × M 种组合；拆了只需处理 N + M 种情况。让大模型根据业务复杂度自行判断阈值。

#### 2. 嵌套深度

检查推演的业务 Case 中，是否存在跨维度逻辑嵌套（如：`if(A) { if(B) { ... } }`）。

| 情况 | 判定 |
|------|------|
| 嵌套层数过多 | 考虑拆分 |
| 嵌套层数较少 | 可合并 |

#### 3. 独立触达率

统计候选维度在上下游场景中，被单独使用（不依赖其他维度）的比例。

| 情况 | 判定 |
|------|------|
| 独立使用频率高 | 物理层拆分（独立列或索引） |
| 总是捆绑查询 | 物理层可合并，逻辑层保持正交 |

### 最终裁决输出格式

```
基于组合乘数评估、嵌套深度评估、独立触达率评估：
最终建议采取 [物理拆分 / 物理合并逻辑拆分 / 完全合并] 方案。
理由：[大模型根据业务场景自行阐述]
```

## 五、案例演示

### 正面案例

订单状态：待支付、已支付、已发货。

| 判定 | 结论 |
|------|------|
| 六域归属？ | 都是交易流程（结果域） |
| 命中十条铁律？ | 无命中→不拆 |
| 复杂度测算？ | 单维枚举，复杂度低→合并 |

结果：`trade_status`：待支付、已支付、已发货

### 反面案例

错误设计：`execution_process: 未执行|执行中` + `is_completed: true/false`

| 判定 | 结论 |
|------|------|
| 六域归属？ | 都是执行进度（结果域） |
| 命中十条铁律？ | 铁律4：同一空间拆成两枚举，违背状态互斥穷尽 |
| 复杂度测算？ | 拆分增加复杂度→合并 |

正确：`execution_status`：未执行、执行中、已完成

## 六、自查清单

| 序号 | 检查项 | 通过标准 |
|------|--------|---------|
| 1 | 六域正交 | 属性归属明确，无跨域混合 |
| 2 | 异空必拆维 | 不同业务空间独立枚举，无综合状态存储 |
| 3 | 并发取积 | 状态并发拆多维，无单枚举堆砌 |
| 4 | 状态互斥穷尽 | 枚举值互斥且穷尽，无盲区 |
| 5 | 时序事实追加 | 结果域追加而非覆盖，有流水表 |
| 6 | 意图实现解耦 | 计划域与执行域分离，无耦合 |
| 7 | 约束显式化 | 业务规则显式为属性，非隐含代码 |
| 8 | 类型极简降级 | 基础类型或值对象，无黑盒结构体 |
| 9 | 流转闭环兜底 | 有起始态+终态，无僵尸态 |
| 10 | 上下文绝缘 | 同名异域隔离，无上帝模型 |
| 11 | 组合检查 | 组合行为=各自规则加起来；非法组合有跨维度条件 |
| 12 | **复杂度测算** | 算组合乘数、嵌套深度、独立触达率，防止过度设计 |
