# 排除特例

> **职责**：做加法。为了技术、性能、开发方便、维护性等，增加一些看似违背教科书的属性。

**何时使用**：建模完成后，需要考虑技术实现时。

---

## 特例清单

| 类别 | 特例场景 | 方向性描述 |
|------|----------|------------|
| **性能优化** | 冗余存储 | 为减少关联查询，将关联数据冗余存储于当前实体 |
| **性能优化** | 预计算结果 | 提前计算并存储结果，避免实时计算开销 |
| **性能优化** | 查询缓存 | 高频查询数据的缓存副本 |
| **历史快照** | 时间点数据 | 保存业务发生时的状态，而非当前最新值 |
| **并发控制** | 乐观锁机制 | 用于防止并发更新冲突的技术标记 |
| **数据管理** | 软删除机制 | 逻辑删除而非物理删除的实现方式 |
| **数据隔离** | 多租户机制 | 数据隔离的技术实现 |
| **数据追踪** | 审计追踪机制 | 记录数据变更的来源和时间 |
| **扩展性** | 动态属性存储 | 不确定扩展属性的存储方案 |
| **数据迁移** | 临时迁移标记 | 批量导入、迁移过程的临时辅助 |

---

## 性能优化类

### 冗余存储

```javascript
// 冗余存储商品名称
class Order {
    productId;      // 关联ID
    productName;    // 冗余存储
    productPrice;   // 冗余存储（下单时价格）
}
```

### 预计算结果

```javascript
class Order {
    items: OrderItem[];   // 明细
    totalAmount;          // 预计算结果
}
```

---

## 历史快照类

### 时间点数据

```javascript
class Order {
    userId;
    userName;         // 下单时的用户名
    userPhone;        // 下单时的手机号
    productPrice;     // 下单时的价格
}
```

## 并发控制类

### 乐观锁机制

```javascript
class Order {
    id;
    version;    // 乐观锁版本号
}
```

---

## 数据管理类

### 软删除机制

```javascript
class Order {
    deletedAt;      // 软删除时间
    deletedBy;      // 删除人
}
```

### 多租户机制

```javascript
class Order {
    tenantId;       // 租户ID
}
```

### 审计追踪机制

```javascript
class Order {
    createdBy;      // 创建人
    createdAt;      // 创建时间
    updatedBy;      // 更新人
    updatedAt;      // 更新时间
}
```

## 扩展性类

### 动态属性存储

```javascript
class Product {
    name;
    price;
    attributes: Map<string, any>;  // 仅用于不确定的扩展场景
}
```

**注意**：
- 主表尽量避免使用 JSON 字段
- 扩展属性应有明确的 KV 表结构
- 仅用于真正不确定的扩展场景

---

## 判定原则

### 判定为特例的条件

1. **有明确的技术目的**：性能、安全、合规等
2. **无业务语义替代方案**：不能用业务属性替代
3. **团队共识**：团队认可该设计的合理性
4. **文档说明**：在代码或文档中说明原因

### 不应判定为特例的情况

1. **懒惰设计**：为了省事而妥协
2. **缺乏思考**：没有评估其他方案
3. **过度使用**：滥用特例掩盖设计问题
