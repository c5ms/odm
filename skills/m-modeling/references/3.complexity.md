# 复杂度测算

> **职责**：防止过度设计。提前预估未来场景，测算可量化指标，决定是否可打破铁律。

**何时使用**：用户明确要求"测算复杂度"或模型复杂度存疑时。

---

## 四步推演法

| 步骤 | 动作 | 目的 |
|------|------|------|
| 1 | 粗建模（快） | 凭经验先把字段定下来 |
| 2 | 过手册（准） | 用十条铁律扫一遍，砍掉明显违背的 |
| 3 | 穷举 Case（全） | 结合上下游，枚举所有业务走向 |
| 4 | 算复杂度账（决） | 算账决定是否真正落地拆分 |

---

## 测算维度

### 1. 组合乘数

**公式**：
```
组合复杂度 = N × M
拆分后复杂度 = N + M
```

其中：
- N = 维度A的枚举值数量
- M = 维度B的枚举值数量

**判定表**：

| 组合乘数 | 判定 | 说明 |
|----------|------|------|
| N × M > 阈值 | 考虑拆分 | 代码维护成本指数上升 |
| N × M ≤ 阈值 | 倾向合并 | 拆了反而增加表关联成本 |

**阈值参考**：

| 业务复杂度 | 建议阈值 |
|------------|----------|
| 简单业务 | 6 |
| 中等业务 | 12 |
| 复杂业务 | 20 |

### 2. 嵌套深度

检查业务 Case 中，是否存在跨维度逻辑嵌套。

**示例**：
```javascript
// 嵌套深度 = 2
if (status === 'APPROVED') {
    if (type === 'URGENT') {
        // 处理逻辑
    }
}

// 嵌套深度 = 3
if (status === 'APPROVED') {
    if (type === 'URGENT') {
        if (priority === 'HIGH') {
            // 处理逻辑
        }
    }
}
```

**判定表**：

| 嵌套层数 | 判定 |
|----------|------|
| ≤ 2 层 | 可合并 |
| 3-4 层 | 考虑拆分 |
| > 4 层 | 必须拆分 |

### 3. 单独使用率

**含义**：这个维度被单独查询的比例，比如"只按支付状态查"不关心发货状态。

**公式**：
```
单独使用率 = 单独查询次数 / 总查询次数 × 100%
```

**判定表**：

| 单独使用率 | 判定 | 建议 |
|------------|------|------|
| > 70% | 物理拆分（数据库层面拆成独立字段） | 独立列或索引 |
| 30%-70% | 逻辑拆分（代码层面分开，存储合并） | 同列存储，逻辑分离 |
| < 30% | 完全合并 | 无需拆分 |


## 测算示例

### 示例1：订单状态拆分

**候选维度**：
- 支付状态：3个值（待支付、已支付、已退款）
- 发货状态：3个值（待发货、已发货、已收货）

**测算**：
```
组合乘数：3 × 3 = 9（中等）
嵌套深度：2层（较低）
单独使用率：60%（中等）
```

**结论**：物理拆分
**理由**：支付和发货有独立的业务流程和查询需求

### 示例2：审批状态合并

**候选维度**：
- 审批状态：4个值（待审批、已通过、已拒绝、已撤回）
- 紧急程度：2个值（普通、紧急）

**测算**：
```
组合乘数：4 × 2 = 8（较低）
嵌套深度：1层（低）
紧急程度单独使用率：10%（低）
```

**结论**：完全合并
**理由**：紧急程度只是审批的附属属性，无独立业务意义

---

## 注意事项

1. **不要过度拆分**：同一件事的不同阶段不强制拆分
2. **考虑实际场景**：理论正确不等于实践最优
3. **留出扩展空间**：为未来变化预留余地
4. **团队共识优先**：复杂度测算结果需要团队认可
