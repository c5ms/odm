## 正面案例：订单状态

订单状态：待支付、已支付、已发货。

| 判定 | 结论 |
|------|------|
| 六域归属？ | 都是交易流程（结果域） |
| 命中十条铁律？ | 无命中→不拆 |
| 复杂度测算？ | 单维枚举，复杂度低→合并 |

**结果**：`trade_status`：待支付、已支付、已发货

## 反面案例：出货单状态合并

### 错误设计

```
status: 草稿 → 已提交 → 已出货 → 已送达
```

**推演问题**：业务要求增加"撤销"功能

| 步骤 | 问题 |
|------|------|
| 1 | 撤销应该在哪个状态后可用？→ 已提交后 |
| 2 | 已出货后还能撤销吗？→ 业务说"特殊情况可以" |
| 3 | 强行插入后，出现什么情况？→ 已出货且已撤销 |
| 4 | 这个状态怎么处理？→ 需要额外字段标记 |
| 5 | 后续又要求"部分撤销"？→ 复杂度继续上升 |

**结果**：状态叠加，后台复杂度暴增。

### 正确设计

```
docStatus:   草稿 | 已提交 | 已撤销
shipStatus:  未出货 | 已出货 | 已送达
```

**组合矩阵（3 × 3 = 9 种组合）**：

|  | 未出货 | 已出货 | 已送达 |
|--|--------|--------|--------|
| 草稿 | ✓ | - | - |
| 已提交 | ✓ | ✓ | ✓ |
| 已撤销 | ✓ | ✓ | ✓ |

**业务含义**：
- 草稿 + 未出货 → 用户正在编辑
- 已提交 + 未出货 → 待仓库发货
- 已提交 + 已出货 → 配送中
- 已提交 + 已送达 → 已签收
- 已撤销 + 未出货 → 撤销成功
- 已撤销 + 已出货 → 撤销但货已发出（需召回）

**判定依据**：
- 说的是不同的事：单据确认 vs 货物配送
- 流转规则不一样：用户操作 vs 物流操作
- 不同人看不同的：销售看单据，仓库看物流

## 案例：报价单与合同

### 错误设计

```
status: 草稿 → 已报价 → 已接受 → 已签约 → 已执行
```

**问题**：报价态和合同态混在一起，无法表达"报价被拒绝后重新报价"

### 正确设计

```
quoteStatus:  草稿 | 已报价 | 已接受 | 已拒绝
contractStatus: 未签约 | 签约中 | 已签约 | 已终止
```

**判定依据**：
- 异空必拆维：报价态和合同态是不同业务空间
- 报价可能多次，合同只有一次

## 案例：审批与退款

### 错误设计

```
status: 待审批 | 审批通过 | 审批中退款中 | 已退款
```

**问题**：混合态 `审批中退款中` 无法表达清晰业务含义

### 正确设计

```
auditStatus:  待审批 | 审批中 | 已通过 | 已拒绝
refundStatus: 无退款 | 退款中 | 已退款 | 已拒绝
```

**组合**：`auditStatus × refundStatus`

**判定依据**：
- 并发取积：审批和退款是独立并发的状态

## 案例：计划与执行

### 错误设计

```javascript
class Order {
    qty;  // 有时是计划量，有时是实际量
}
```

**问题**：无法区分"预期"和"实际"

### 正确设计

```javascript
class Order {
    plannedQty;   // 计划域：预期数量
    actualQty;    // 执行域：实际数量
}
```

**判定依据**：
- 意图实现解耦：计划值和实际值分开

## 案例：约束隐含

### 错误设计

```javascript
class Order {
    amount;
    
    validate() {
        if (this.amount > 10000) throw Error();
    }
}
```

**问题**：约束藏在代码里，不透明

### 正确设计

```javascript
class Order {
    amount;
    maxAmount: 10000;  // 约束域：显式化
}
```

**判定依据**：
- 约束显式化：业务规则变成属性
